four implementation plans. This records what was closed and how it was verified.
`docs/remaining-work.md` is the other half, everything still open.

implemented, already fixed, and still open, which made them expensive to read and easy

## Application findings

### F6: a nullable id turned one drink into a failed history request

`alcohol_volume_id`, `consumption_type_id` and `alcohol_type_id` are all nullable, and
nothing treated them as such. Both name collectors passed them straight into Spring Data's
`findById`, which rejects a null id with `IllegalArgumentException`, and `DrinksController`
compared `getAlcoholTypeId().equals(beerId)`, dereferencing the same nullable column.
Either way a single incomplete row turned the entire day's history into a 500.

`RecommendationService.withName` already wrapped the identical call in a try/catch, so the
hazard was known in one place and missed in the other.

Each id is now checked before its lookup and the type comparison goes through
`Objects.equals`. An incomplete row degrades to the placeholder name the collectors already
had for the not-found case, which is why nothing else needed to change.

**The tests are the interesting part.** Mockito returns an empty `Optional` for
`findById(null)` by default, which hides the defect completely, and is exactly why the
existing suite passed straight over it. The new tests stub the mocks to throw the way
Spring Data actually does.

Verified against the live stack: a row inserted with every id null now renders as
"Unknown alcohol Unknown volume" and the day returns 200.

### F9: the volume followed the JVM's default locale

`String.format("(%s - %.2fl)", ...)` with no `Locale`, so the volume rendered as `0,50l`
wherever the default is comma-decimal. Invisible in the container, which runs with a dot
locale, and it would have changed silently with the JVM's. Pinned to `Locale.ROOT`, with a
test that sets a comma-decimal default around the assertion.

### F2: `quantity: 0` was a 500

`quantity` is the number of rows to write and nothing validated it. A `0` or a negative made
the `IntStream` range in `saveDrink` empty, so `saveAll(...).getFirst()` threw
`NoSuchElementException`: a 500 for a plainly bad request, from a field taken straight off
the request body.

The finding left the behaviour open, reject or treat `0` as `1`. It rejects with a 400,
because 0 rows is not something a client can have meant and silently writing one row invents
data the user did not ask for.

`@Max(100)` was added beyond the finding: `quantity` multiplied rows written per request with
nothing capping it, so one request could ask for a million. 100 is an order of magnitude
above the 9 the UI allows.

`spring-boot-starter-validation` is now declared explicitly. `hibernate-validator` was
already on the classpath, but only transitively through
`springdoc-openapi-starter-webmvc-ui`. Request-body constraints **fail open**: with no
validator present, `@Valid` is silently ignored and the 500 comes back with nothing to show
that anything changed.

### F7 and F8: the alcohol type write path

Both were the author's own TODOs.

`// TODO ResponseEntity 404`. An unknown alcohol type made `saveVolumeForAlcoholType` return
`new AlcoholVolume()`, so the client got a 200 carrying an all-null volume and no way to tell
success from failure. The repository now returns `Optional` and the controller answers 404.
No web change was needed: `NewVolumePage` already wraps the call in a try/catch that
navigates to the error page, and axios rejects a 404, so the outcome moved from "claims
success, saved nothing" to an honest failure.

`// TODO in transaction`. `createAlcoholType` wrote volumes, then the type, then the subtypes
as three separate operations, so a failure part way left orphaned volume rows and a type with
no subtypes. Now `@Transactional`. `saveVolumeForAlcoholType` got the same treatment for the
same reason.

The rollback is proven against a real Postgres, because mocks cannot show it. Two details in
that test are load-bearing and commented as such: `@DataJpaTest`'s own transaction is
suspended with `NOT_SUPPORTED`, because otherwise the surrounding rollback makes the
assertion pass whether or not the code under test is transactional at all; and each test uses
its own `userId` with delta counts, because suspending that transaction means whatever commits
stays committed. Verified by mutation that removing `@Transactional` turns the test red.

### F4: the save counter was AtomicInteger shaped, not atomic

The finding called this low priority and mild. Measuring it turned up a second race the
finding did not mention, with a larger effect than the one it did.

| Step | Was | Now |
|---|---|---|
| Create the counter | `get(key, Class)` then `put` | `get(key, valueLoader)`, one atomic compute on Caffeine |
| Increment | `counter.set(counter.get() + delta)` | `addAndGet(delta)` |
| Reset at the threshold | `if (get() >= N) { evict; set(0); }` | `compareAndSet(updated, 0)` gates the evict |

The increment is the race the finding described. **The reset is the one that was missed, and
it dominates**: every thread that observed a value over the line evicted and reset. Measured,
8 threads x 500 saves at a threshold of 5:

```
old: evictions=1436 1382 1371 1411 1524     (800 were due)
new: evictions=797  797  797  798  794
```

So the cache was being invalidated nearly twice as often as intended, not "a little later than
intended".

The test's upper bound is an invariant rather than a measurement: every eviction consumes at
least the threshold and nothing else removes counts, so N saves can produce at most
N/threshold evictions however the threads interleave. That is the assertion with teeth, and
the old implementation misses it by 70%. It is sound rather than exhaustive: correct code
cannot fail it, so it will not flake red.

### F5: the token refresh interval was never cleared

`KeycloakProvider` started `setInterval` in its init effect and returned no cleanup. Harmless
in the running app, where the provider lives as long as the app does, but it leaks across hot
reloads and across tests: a torn-down provider kept calling `updateToken` and, on rejection,
kept calling `logout`.

**The cleanup deliberately sits outside the `didInit` guard**, and this is the part that is
easy to get wrong. The interval is created after `keycloak.init` resolves, which is after
Strict Mode has already double-invoked the effect, so a cleanup returned from inside the
guarded branch would be the early return's `undefined` on the second pass and would never
clear anything. Reading a ref in an unguarded cleanup means the first pass's cleanup is a
no-op and the second, the only one React keeps, clears the live interval.

Two adjacent behaviours that had no coverage at all are now covered too: a rejected refresh
logs out, and initialization reporting not-authenticated never starts the interval.

### F10: the save button had no accessible name

The `DetailedPage` save `Fab` contains only a `SaveIcon`, so a screen reader announced the
primary action of that screen as "button". Now labelled, and both selectors that were working
around its absence are gone: the unit helper no longer digs through `getByTestId('SaveIcon')`,
which MUI strips from production bundles, and the e2e spec no longer falls back to
`button.MuiFab-root`.

**A wrong turn worth recording.** The helper was first written as
`getByRole('button', { name: /save drink/i, hidden: true })`. That made the suite flaky: two
full parallel runs in three failed while passing every time in isolation. Confirmed against
the branch point that the old helper was stable, so the flake was introduced, not
pre-existing. The cause is the `<Zoom in={isFormValid}>` wrapper, which takes the Fab out of
the accessibility tree while the form is incomplete, correct behaviour that makes a role query
depend on transition timing under load. The helper uses `getByLabelText`, which is
deterministic in both states; the role query is asserted once, where the button is usable.

### IDOR leftovers: stop sending, and stop accepting, an ignored userId

The IDOR fix made every endpoint derive the caller from the JWT subject, but the client kept
sending a `userId` in eight places and three DTOs kept a component the client could populate.
All inert, and all reading as though the client's claim about who it was still counted.

Four query parameters bound to no controller parameter (`getAlcoholTypes`,
`getSubtypesByAlcoholType`, `getBrands`, `getBeerFlavours`) and four body fields the server
overrode or dropped. Six `if (!userId) throw` guards went too, along with `getCurrentUserId`,
which existed only to fill those payloads.

`NewBeerFlavour.userId` was never read by anything and is gone. `Drink`, `NewAlcoholEntry` and
`NewAlcoholSubtype` still need the field, because that is where `withUserId` puts the
authenticated id, so it is `@JsonProperty(access = READ_ONLY)` instead: **Jackson will not bind
a client-supplied value at all**. Overriding it already closed the IDOR; refusing to bind it
means a future call site that forgets to override gets a `null` rather than whatever the caller
asked for.

The four tests for this deserialise the payloads directly, because that is the only place
`READ_ONLY` is visible: the controller tests pass either way, since the override happens before
the assertion. Verified by mutation and against the live stack, where a spoofed userId in the
body saves under the JWT subject.

The sixteen endpoint tests that pinned the old behaviour now pin the opposite, with exact-match
assertions rather than `objectContaining`, because the negative half is the point.

## Privacy

### GDPR item 7: SQL statement logging

`spring.jpa.show-sql=true` was hardcoded on in every environment. The review rated it lower
severity than it looks, since Hibernate does not log bound parameters by default, and asked for
two things to be confirmed: whether anything downstream captures parameters anyway, and what the
retention and access control are wherever the logs land.

Neither is answerable from this repository, and that is the point. Statements still carry the
user UUIDs whose rows they touched, so leaving this on copies consumption data into a log sink
governed by whatever policy that sink happens to have. Now `${JPA_SHOW_SQL:false}`, threaded
through the chart as `jpa.showSql`, so debugging a query in test is a values change and a
redeploy rather than an image rebuild. The compose stack keeps it on: seeded demo data only.

Everything else in the GDPR document is still open. See `docs/remaining-work.md`.

## Found while doing the rest

None of these were in any document.

### The CI integration-test guard covered three of seven classes

The guard that fails CI when the Testcontainers tests silently skip already existed in both
backend workflows. It named three classes. There are seven. It also built the report path by
prefixing one hardcoded package, so a class outside `repository.postgres.schema` could not have
been checked even if it had been listed.

**Four of seven integration test classes could have skipped entirely and both workflows would
have gone green, printing "Integration tests ran against a real Postgres."**

An allowlist that has to be extended by hand is the wrong shape for this: it is exactly the kind
of maintenance nobody remembers, and its failure mode is silent and reassuring. The list now
comes from the source tree. The logic moved to
`backend/scripts/assert-integration-tests-ran.sh`, which both workflows call, because it was
duplicated verbatim and the bug therefore existed twice.

### The end-to-end gate could never pass

The e2e workflow had been failing on `main`, and not on a test: it timed out after five minutes
waiting for a stack that was already up. Since running that suite on `main` only exists to gate
a release, **the gate was red and had stopped gating anything.**

The readiness loop polled `http://localhost:8080/actuator/health` from the host. Actuator moved
entirely onto the management port in `0ad6935`, and compose deliberately does not publish that
port. The subtlety is that a request to the main port does not 404:
`.anyRequest().authenticated()` runs ahead of any route-not-found handling, so it answers 401,
`curl -fsS` treats that as failure, and the loop exhausted all sixty attempts every run.

Confirmed against the live stack:

```
host          :8080/actuator/health  ->  401, curl -fsS fails
in-container  :8081/actuator/health  ->  200 {"status":"UP"}
```

The probe now runs inside the container against the management port, which is what
`compose.yaml`'s own healthcheck already does.

### The coverage ratchets had stopped ratcheting

The backend floor had not moved since the suite was introduced: 78% against a measured 90.50%,
twelve points of slack. Coverage could have fallen by a tenth of the codebase without CI
noticing. Raised to 90%, and the web thresholds to the measured values. Each now carries the
date and the measurement in a comment.

### The web bundle was one chunk

660 kB in a single chunk, from `docs/DEPLOYMENT.md`'s follow-ups. Every page imports MUI, so
one eager bundle meant the first paint waited on the five form pages and the history screen as
well as the screen being opened.

| | chunks | largest | gzip | size warning |
|---|---|---|---|---|
| before | 1 | 659.41 kB | 204.29 kB | yes |
| after | 25 | 208.61 kB | 66.14 kB | gone |

First paint on the home route is now roughly 170 kB gzip rather than 204. What remains eager is
React plus MUI core and keycloak-js, which are needed before anything can render.

`App.tsx` had no test and 0% coverage, which mattered more once the routes became lazy: a wrong
path or a typo in a dynamic import is a runtime failure on navigation, not a compile error, and
the page would simply never arrive. There is now a case per route. That test more than paid for
the file's growth, which is why the coverage numbers went up rather than down.

One test was written and then dropped rather than left in: an assertion that the Suspense
fallback is visible. It passes alone and fails after the route tests, because by then the page
modules are in the import cache. Order-dependent tests are worse than absent ones.

## How this was verified

Unit and integration suites are the floor, not the evidence. Each fix also got at least one of:

- **Red before green.** Every new test was confirmed failing against the pre-fix code, with the
  real exception where there was one.
- **Mutation.** Where a test could plausibly have passed for the wrong reason, the fix was
  reverted to check the test actually caught it: `@Transactional`, the `READ_ONLY` annotations,
  the cache atomicity, the `aria-label`.
- **Measurement.** The cache races and the bundle sizes are numbers taken before and after, not
  claims.
- **The live stack.** `docker-compose up --build`, then a real Keycloak token and direct calls:
  quantity 0, -1 and 101 rejected with 400 and 1 accepted; a spoofed userId in the body saved
  under the JWT subject; an unknown alcohol type answering 404 and a known one 200; a
  deliberately inserted all-null drink row rendering as a placeholder instead of failing the
  day; and the four GET endpoints working with no `userId` parameter.
- **The browser.** All six Playwright journeys pass against that stack, through the real
  Keycloak login. That run is also what proves the `aria-label` selector works on a production
  bundle where MUI strips icon test ids, and that the lazy routes load.
- **CI.** Every branch in the stack is green, which includes the new guard script running on a
  real runner.

## What was deliberately not done

See `docs/remaining-work.md` for the full list with instructions. The short version: the GDPR
work beyond item 7 needs a legal determination first or is a feature in its own right; Prometheus
needs a decision about how a scraper authenticates; SHA-pinning the actions and digest-pinning the
base images are maintenance tradeoffs the earlier review deliberately left to the repository
owner; and four leftover namespaces cannot go until production is cut over.
